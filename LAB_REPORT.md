## Часть 1. Выбор и обоснование средств обработки информации

### 1. Описание системы и ее бизнес-процессы
Информационная система предназначена для перевода бумажного учета книг и читательских билетов колледжа в цифровой формат. Автоматизации подлежат три ключевых бизнес-процесса:
* **Поиск и бронирование книг:** удаленный поиск литературы студентами в электронном каталоге.
* **Выдача и прием литературы:** фиксация сотрудником библиотеки факта движения книги.
* **Контроль задолженностей:** автоматическое выявление просроченных книг.

### 2. Цели создания ИС
* Сокращение времени обслуживания одного читателя в 2–3 раза.
* Обеспечение оперативного контроля над фондом в 20 000 единиц хранения.
* Исключение ошибок "человеческого фактора" при ведении журналов учета.

### 3. Обоснование технологического стека (ПО)
* **Тип разработки:** Кастомная разработка. Готовые решения не учитывают специфику колледжа, а платформы вроде 1С требуют дорогостоящего лицензирования.
* **СУБД:** Microsoft Access. База данных хранится в локальном файле `library_db.accdb`, что упрощает перенос и резервное копирование. Лимита в 2 ГБ более чем достаточно: текстовые данные на 20 000 книг и 1 000 пользователей займут не более 50–100 МБ. База данных целиком кэшируется средствами ОС для обеспечения максимального быстродействия.
* **Backend:** Python (FastAPI). Обеспечивает высокую скорость разработки, минимальное потребление ресурсов сервера и простое построение архитектуры API.
* **Frontend:** HTML5 / JavaScript. Позволяет создать отзывчивый интерфейс каталога с динамическим поиском книг в реальном времени без перезагрузки страниц.

### 4. Аппаратные требования к серверу
Для обеспечения стабильной работы при пиковой нагрузке в 50–70 одновременных пользователей (во время перерывов между парами) выбрана следующая конфигурация VPS:
* **CPU:** 2 vCPU (архитектура x86-64) — для параллельной обработки поисковых запросов.
* **RAM:** 2–4 GB RAM — обеспечивает одновременную работу ОС Ubuntu Server и Python-скриптов.
* **Диск:** 30–40 GB SSD / NVMe — под систему, логирование и ежедневные автоматические бэкапы.
* **Сеть:** 100 Мбит/с — комфортная скорость отдачи веб-страниц.

### 5. Итоги, плюсы и риски стека
* **Плюсы:** Экономическая выгода (ПО с открытым исходным кодом), высокая скорость работы интерфейса и простота резервного копирования файла БД.
* **Риски:** Увеличенные сроки разработки с нуля и необходимость поддержки системы силами штатного ИТ-отдела колледжа.

## Часть 2. Распределение ролей и регламент работы команды

### 1. Состав команды и роли
* **Корепанов Роман (Team Lead / Архитектор):** Отвечает за координацию команды, проектирование таблиц в БД Access, проведение код-ревью и финальное слияние веток в `develop` и `main`.
* **Халтурина Екатерина (Backend-разработчик):** Отвечает за разработку серверной логики авторизации на Python и прямое подключение к файлу базы данных.
* **Перевозчикова София (Frontend-разработчик / QA):** Разрабатывает веб-интерфейс каталога, ведет журнал изменений CHANGELOG.md и выполняет ручное тестирование API.

### 2. Регламент работы с Git (Workflow)
Разработка велась по упрощенной модели **GitFlow**:
* `main` — стабильная ветка с рабочим релизом. Прямые коммиты запрещены.
* `develop` — основная интеграционная ветка, куда сливается готовый код.
* `feature/...` — персональные ветки разработчиков для изоляции кода задач (например, `feature/backend-auth`).

**Правила оформления коммитов:**
Сообщения коммитов строго начинаются со спецификатора: `feat:` (новый функционал), `fix:` (исправление багов/конфликтов), `docs:` (документация).
